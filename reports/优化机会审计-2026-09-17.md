## P0 · 建议优先处理

### P0-1 图片体积失控（最严重）

**证据**

```
首页 /en          143 KB HTML，30 张图，合计 18.19 MB
产品页            5 张图，合计 3.43 MB
Beanie 落地页      9 张图，合计 3.69 MB
最重的 5 张：
  2393 KB  photo-1556306535-0f09a537f0a3?auto=format&fit=crop&q=80&w=800
  2167 KB  H77e3adefc7b64346986b3b9b66ab5940x.png   ← 导航 logo
  1968 KB  Ab257aa93655344cdb3405b61cb0622bfS.png
  1766 KB  A08f3026e946b4a238d225173ff266ad8N.png
  1459 KB  Factory-Price-100-cotton-5-Panel-Gorras.png
30 张里有 17 张 >100 KB
```

**根因**
- 全站用的是裸 `<img src="...">`，没有走 `next/image`，所以没有自动 WebP/AVIF、没有响应式尺寸
- **导航 logo 是 2.17 MB 的 PNG，却渲染在 `h-8`（32px）**，而且被 `<link rel="preload" as="image">` 放进了关键路径 —— 每一页、每个访客都要先下 2 MB
- 老产品图（`sc01.alicdn.com/kf/H...png`）没带尺寸参数；新加的 10 款带了 `_960x960q80.jpg`（几十 KB），说明加参数就能解决

**修法**
1. logo 换成 SVG 或压缩到 <10 KB 的 PNG/WebP，同时替换 Organization schema 里的 `logo` 字段（现在指向同一个 2 MB 文件）
2. 老产品图统一补 `_960x960q80.jpg` 后缀（阿里 CDN 的压缩变体）
3. 把 `<img>` 换成 `next/image`，或至少补齐 `width`/`height`（当前首页 24/32 有、落地页 0/10 有 → 有 CLS 风险）
4. 首屏图 `priority`，其余 `loading="lazy"`（首页 32 张里只 23 张 lazy）

**预期收益**：首页图片从 18 MB 降到 1-2 MB 量级。这是目前对 LCP 和移动端体验影响最大的单项。

### P0-2 产品页 FAQPage 结构化数据缺失

**证据**

```
产品页有可见 FAQ（页面上能数到 5 组问答），但：
  FAQPage schema: false
全站 FAQPage 覆盖：14/88
  ✓ 首页、/pricing、5 个对比页（各 en/es）
  ✗ 23 个产品页 × 2 = 46 个 URL
```

**根因**：`products.ts` 里每款产品都写了 `faqs[]`（2 条/款，共 46 组），产品页也确实渲染了出来，但 `product/[id]/page.tsx` 的 JSON-LD 只输出了 `Product` + `BreadcrumbList`，没有把 faqs 转成 FAQPage。

**修法**：复用 `ComparisonShell` 里已有的 FAQPage 生成逻辑，把 `hat.faqs` 一起输出。

**预期收益**：46 个 URL 直接获得富媒体问答展示资格；对 AI 检索（ChatGPT/AI Overviews）尤其友好 —— 这本就是对比页当初加 FAQPage 的原因。

### P0-3 产品页内链只有 6 条

**证据**

```
产品页    6 个内链 / 183-261 词   ← 全部 46 个页面
落地页   29-39 个内链 / 485-941 词
对比页   29-32 个内链 / 1162-1996 词
首页     43 个内链 / 2005 词
```

**根因**：产品页除了导航和 3 张 Related 卡片，没有任何正文内链。

**修法**（每页加 5-8 个上下文内链）
- 指向所属品类落地页（如 trucker 产品 → `/custom-trucker-hats`）
- 指向相关对比页（如面料类 → `cotton-twill-vs-brushed-cotton-vs-canvas`）
- 指向 `/pricing`、`/materials`、`/guide`
- 同品类其他产品（Related 已经做了同品类优先，可再加"同系列"区块）

**预期收益**：把 46 个孤岛页接进权重网络，是提升收录率和排名最直接的一招。

### P0-4 移动端完全没有导航

**证据**

```
app/[locale]/page.tsx:153   <nav className="hidden md:flex ...">
全库 grep md:hidden|Menu|hamburger|mobileNav → 0 命中
```

**影响**：<768px 的手机上，页头只剩 logo + WhatsApp 按钮 + 语言切换。刚做好的两级 Products 下拉在手机上完全不可用。这与"让买家从上方选择产品"的目标直接冲突。

**修法**：先把散落在约 15 个内联 header（外加 `LandingShell`、`ComparisonShell`）的导航抽成统一 `SiteHeader`，再加汉堡菜单 + 抽屉。

**注意**：这个重构本身有价值 —— 导航改一次要动 20 个地方的坑已经踩过三次了。

### P0-5 西语产品页是英文内容

**证据**

```
23 款产品的 title 与 meta description 在 /en 和 /es 上完全相同
例：/en/product/custom-foam-front-trucker-hat
    /es/product/custom-foam-front-trucker-hat
    都叫 "Custom Foam Front 5 Panel Trucker Hat | Custom Wholesale | BD Hats"
正文词数也几乎一致（252 vs 254），说明正文也是英文
```

**为什么现在还不算致命**：hreflang 配置是**正确**的（en/es/x-default 三条齐全、自引用、canonical 各指自己），Google 会正确处理为语言互替版本，不会判定为作弊。

**但仍然要修**：西班牙语买家点进来看到的是英文产品页，转化直接受损；且 11 个落地页已经做了西语化，产品页没跟上，体验不一致。

**修法**：`products.ts` 的 `Product` 接口加 `nameEs` / `descEs` / `fullDescEs` / `specsEs` 字段（可先只做 name + desc + fullDesc），产品页按 `useLang()` 取。25 款产品的西语化需要你或翻译校对。

**修法**：每条压到 150-160 字符，把关键词和数字留在前 120 字符内。

### P1-2 title 过长：69/88 页 >62 字符

根因是根 layout 的模板 `%s | BD Hats` 叠加在已经带后缀的页面标题上。最长 78 字符：

```
China vs Vietnam vs Bangladesh: Where Should You Source Custom Hats? | BD Hats   (78)
Snapback vs Strapback vs Buckle: Which Closure Should You Choose? | BD Hats      (75)
Cotton Twill vs Brushed Cotton vs Canvas Caps: Which to Choose? | BD Hats        (73)
```

**修法**：对比页/落地页标题去掉自带的 `| BD Hats`（历史上已修过一次，新增页面又带上了），或缩短前半句。

### P1-3 BreadcrumbList 缺失

```
有面包屑：首页、/guide、23 个产品页（×2）
无面包屑：11 个落地页、5 个对比页、/pricing、/materials、/about（共 38 个 URL）
```

**修法**：给 `LandingShell` 和 `ComparisonShell` 加统一的面包屑 + schema，改两个组件就能覆盖 32 个 URL。

### P1-4 产品页内容过薄

46 个产品页 183-261 词。最薄的是 `breathable-custom-embroidered-6-panel`（183 词）、`personalised-two-tone-a-frame-cap`（183 词）。

**修法**：每款产品补 150-250 词的独有内容 —— 工艺细节、适用场景、常见定制问题。**不能用模板批量生成**，那会制造重复内容。真实素材需要你提供（每款的实际工艺差异、打样注意点）。
